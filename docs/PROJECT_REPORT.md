# ThreatGuard ML — academic project report

**Assessment:** DevSecMLOps Internal 2  
**Level:** B.Tech CSE, medium difficulty  
**Benchmark support:** Official UNSW-NB15 prepared CSV partitions  
**Actual local evaluation:** Synthetic development data only

## Abstract
ThreatGuard ML implements a reproducible network-flow classification baseline with validated data,
train-only preprocessing, Random Forest learning, held-out evaluation and versioned local artifacts.
An authenticated FastAPI service validates inference batches and reports possible feature-distribution
drift. The implementation joins ML engineering with practical application security and CI gates.

## Problem and objectives
A model alone is insufficient for a secure deployment. The project aims to prevent label/preprocessing
leakage, handle heterogeneous flow features, expose controlled predictions, retain training provenance,
apply measurable model-quality gates, and monitor distribution changes without claiming unsupported
production accuracy or automatic performance degradation.

## Method
1. Inspect local CSV headers, target values, features, missingness and class distributions.
2. Exclude target labels, identifiers and unknown columns; convert supported feature types.
3. Use independent external testing or seeded stratified feature-group splitting; count removed overlaps.
4. Fit median numerical and constant categorical imputers on training only, then one-hot categories.
5. Train a reproducible class-balanced Random Forest and evaluate the held-out partition.
6. Save metrics, schema, data digests, library versions and training-only drift reference.
7. Activate a candidate only when F1/recall gates pass; load local trusted artifacts for the API.
8. Validate/authenticate bounded requests and compute numeric PSI or categorical total variation.

## Evaluation
Accuracy, precision, recall, F1, confusion matrix and per-class metrics are generated by scikit-learn.
Binary precision/recall/F1 use attack class 1; multiclass scores use macro averaging. The default
binary threshold is fixed at 0.5 before testing. The final synthetic run used 1,200 artificial rows,
900 training and 300 held-out rows; precise metrics are in reports/verified-synthetic/evaluation.json.
No real UNSW-NB15 result is claimed, and synthetic scores have no real-network interpretation.

## API and security
Health, model information, prediction, metrics and drift endpoints are implemented. Except health,
endpoints require an environment key. Exact feature/type validation, request-body limits, rate limits,
safe errors and read-only model deployment reduce common risks. Joblib remains executable
deserialization and requires administrator-controlled artifacts; a hash only detects corruption.

## Verification and limitations
See reports/VERIFICATION.md for pytest, lint, real HTTP smoke checks and actual security-tool outcomes.
Tests cover dataset errors, reproducibility, corrupt artifacts, authentication, malformed/missing fields,
batch limits, rate limits and stable/shifted distributions. Docker and real-data evaluation remain
manual steps where prerequisites are absent. Historical lab data may not represent deployment traffic.

## Discussion and future work
Drift flags input-distribution changes, not accuracy loss. A labelled performance monitor is needed
before approving retraining. Production also requires a flow extractor, temporal validation, calibrated
probabilities, signed artifacts, shared state, TLS and governed releases. The delivered project is a
working academic pipeline and secure API baseline, not a deployed intrusion-prevention appliance.
